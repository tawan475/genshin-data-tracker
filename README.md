# teyvat.me-tracker

Tracks Genshin Impact inventory snapshots (GOOD format) uploaded by
[irminsul](https://github.com/tawan475/irminsul) or imported by hand. One
Cloudflare Worker serves the Vue dashboard as static assets and the API under
`/api`, backed by D1. Production: https://teyvat.me

The old address, https://genshin-tracker.475.dev, is a second custom domain
on the same Worker: its `/api` keeps answering (installed irminsul copies
post there) and its pages go to teyvat.me, path and all (see
[The old address](#the-old-address)). Cookies are per host, so people sign
in again once on teyvat.me.

## Layout

| Path | What |
|---|---|
| `apps/tracker/src` | Vue 3 dashboard |
| `apps/tracker/worker` | Hono API on Workers, Drizzle schema for D1 |
| `apps/tracker/migrations` | SQL migrations generated by drizzle-kit, applied by wrangler |
| `packages/shared` | Code both sides use: GOOD types, snapshot codec, static dictionary, settings, limits |
| `@gdt/game-data` | Not in this repo: the game data (achievements, planner costs and math, material index, catalog, image names) from the private [tawan475/genshin-game-data](https://github.com/tawan475/genshin-game-data), a git dependency of `apps/tracker` pinned to a release tag; see [Game data](#game-data) |

## Development

```bash
pnpm install                              # needs read access to tawan475/genshin-game-data (see Game data)
pnpm dev                                  # Vue app + Worker (workerd) on one Vite server
pnpm test                                 # shared tests (Node) + worker and app helper tests (workerd + local D1)
pnpm --filter @gdt/tracker db:generate    # after editing worker/db/schema.ts
pnpm --filter @gdt/tracker db:migrate:local
pnpm --filter @gdt/tracker db:generate:live        # after editing worker/db/live-schema.ts
pnpm --filter @gdt/tracker db:migrate:live:local   # the gdt-live database (live sync)
pnpm --filter @gdt/tracker cf-typegen     # after editing wrangler.jsonc
```

Set `GDT_GOOD_SAMPLES_DIR` to a folder of real GOOD exports to also run the
codec round-trip over them (they are personal data and never committed).

## Game data

`@gdt/game-data` comes from the private repository
`tawan475/genshin-game-data`, pinned in `apps/tracker/package.json` to a
release tag (`github:tawan475/genshin-game-data#v7.1.0`); the lockfile
records its commit. Each tag is a release commit carrying the built package
(JS + `.d.ts` + `data/*.json`), so the install runs no build. Import paths
are the package's: `@gdt/game-data`, `@gdt/game-data/planner-math`,
`/catalog`, `/image-url`, `/images`, `/good-key`, `/data/<file>.json`. Vite
serves it unbundled (`optimizeDeps.exclude`), so each data file stays its
own lazy chunk.

- **Access.** `pnpm install` fetches it with git. Locally your own GitHub
  credentials do (Git Credential Manager, `gh auth setup-git` or SSH);
  without read access to that repository the install fails. CI uses the
  `GAME_DATA_DEPLOY_KEY` secret, the private half of a read-only deploy key on
  that repository (`.github/actions/setup`; a `GAME_DATA_TOKEN` fine-grained
  token works too).
- **Updates arrive by themselves.** The data repository builds, cross-checks
  and releases every new game patch; `game-data-bump.yml` checks for a new
  release every 3 hours (or on a `repository_dispatch` `game-data-release`, if
  the data repository has a `TRACKER_DISPATCH_TOKEN`), and `.github/workflows/game-data-bump.yml` bumps
  the tag on a branch, runs the tests, type check and build, merges, and
  deploys. A daily run picks up a release whose dispatch was missed. A
  failing check leaves the pull request open with `needs-human`.
- **Bump by hand:** `pnpm --filter @gdt/tracker add
  "@gdt/game-data@github:tawan475/genshin-game-data#<tag>"`.
- **Work against a local checkout** of the data repository (a sibling
  `../genshin-game-data`): make a release commit and tag there as its
  release workflow does, then `pnpm --filter @gdt/tracker add
  "@gdt/game-data@git+file:///<absolute path>/genshin-game-data#<tag>"`.
  Switch back to the `github:` spec before pushing (CI can't see your disk).
- What stays here: app logic over the data (`src/data/seelie.ts`,
  `achievement-progress.ts`, `account-player.ts`, `game-meta.ts` for
  rarity/element/weapon type from the data's catalog), and the fixed
  artifact stat tables (`src/data/artifact-stats.ts`).
- `toGoodKey` is in both `packages/shared` and the game data
  (`@gdt/game-data/good-key`); `src/lib/__tests__/good-key-sync.test.ts`
  fails until the two agree.

## Storage model

A snapshot row holds its capture times, sizes, the first 47 bits of its
content hash, the ids of its ten sections (characters, weapons, artifacts,
materials, achievements and irminsul's player, achievement times, character
extras, anecdotes and tasks) and `meta`: the summary the list views show, the GOOD
header and the player values that move with every login (resin, AR EXP).
Sections are stored once per account in `section_blobs` under the first 8
bytes of their content address, with an integer id. Artifacts live in an
immutable per-account catalog, packed many to a row in `artifact_chunks`
(about 10 bytes a piece); each snapshot records which catalog entries it
held and their location/lock state at the time.

A section blob is a format byte and a payload: canonical JSON or a binary
layout (varints, column by column, zigzag deltas; checked by decoding it back
before it is trusted), stored as is or DEFLATEd (fflate), optionally with its
*base* section as the preset dictionary. Materials, artifacts and achievement
times are usually stored as a delta against a full base section of the
latest snapshot (for materials, the keyframe), never against another delta;
any full section is compressed against the account's previous standalone
section of its kind while that halves it. A new base is stored once the
delta passes √(2·25 B·base size), the cheapest point in the cost model in
`sections.ts` (re-measured for v2 in `store-v2.ts`). So decoding needs at
most three blobs. The content hash is still taken over the canonical JSON of
the full forms, so a capture uploaded again is recognised whatever its
storage. The formats are defined in `packages/shared/src/codec`
(`section-blob.ts`, `section-binary.ts`, `snapshot-meta.ts`,
`catalog-binary.ts`, `store-v2.ts`) and must stay decodable forever: only
add new format values.

**Storage v1** (migration 0016 and before): rows named sections by 32-digit
hex hashes in `blobs` (deflated JSON) and kept the summary as JSON; the
catalog was one `artifacts` row per piece. Readers understand both. Repack
converts v1 to v2, a batch at a time: each row's sections are re-encoded,
decoded back and compared with the v1 decode, and only an exact match is
written (with the row, in one batch); the catalog moves into chunks the same
way. `GET /api/admin/repack` says what is left, `POST
/api/admin/repack?limit=100` converts (both need `x-diag-key`; `after` skips
rows that did not convert, which the answer lists and the log names by id).
The daily maintenance repacks too when the `REPACK_CRON_LIMIT` var is set.
Migration `0017_drop_storage_v1` (its own commit, shipped only once repack
reports nothing left) drops the v1 columns, the `blobs` table and the
redundant `(account_id, taken_at)` index; it refuses to run while a v1 row
remains, and the Worker already runs on either schema. `artifacts` stays:
imports insert new pieces there to get their ids (AUTOINCREMENT) and move
them into a chunk in the same batch as the snapshot.

irminsul's own top-level keys are sections of their own, each optional and
range-checked again on import: `gi_player` (AR, World Level, UID… as read at
login) as `player`, `gi_achievement_times` (finish times, unix seconds) as
`achievementTimes`, `gi_characters` (friendship, obtained date) as
`characterExtras`, `gi_anecdotes` (the Travel Accounts book: state and finish
count per met anecdote, unlocked areas, stamp progress) as `anecdotes`,
`gi_tasks` (contract v1, the game's state at login: commissions done today,
the Abyss period's stars, who is out on an expedition and when they are back,
the realm currency jar, Welkin days; each part kept only when all of it is in
range) as `tasks` (`snapshots.tasks_ref`, migration 0028), and Teyvat.me
Capture's `gi_collections` (from 1.3.0: the Radiant Spincrystals in the
Serenitea Pot's music list by item id; each part kept only when every entry
passes; later parts append) as `collections` (`snapshots.collections_ref`,
migration 0030), and from Capture 1.4.0 gi_collections' other parts (the
Archive by tab, defeats per Living Being, the Adventurer Handbook, Aranara,
TCG cards and decks) as `collections2` and `gi_wardrobe` (outfits, gliders,
weapon skins and trails owned and worn, saved teams) as `wardrobe`
(`snapshots.collections2_ref` / `wardrobe_ref`, migration 0031; the
deployed collections layout cannot learn new parts, hence the second
section; its layout and the wardrobe's are tagged, so an older build skips
a part it does not know). Capture 1.5.0's `gi_collections.recipes` (recipe
id -> proficiency) is collections2's part `p`. Capture 1.6.0's
`gi_exploration` (Statues, offerings, map points and areas per scene,
exploration points per area, reputation) is `exploration`
(`snapshots.exploration_ref`, migration 0032; tagged like the wardrobe; a
relogin with nothing new stores 0 bytes). Capture 1.7.0's keys: gi_tasks'
`weeklyBosses`, `respawns` and `arRewards` join the `tasks` section (as JSON
letters `q`/`m`/`k`: the deployed binary layout refuses new flags, old
decoders ignore unknown letters), gi_collections' `hangouts`,
`monstersSeen` and `blueprints` are collections2 parts `u`/`m`/`f`, and
`gi_achievement_progress` + `gi_events` are the `progress` section (kind 15,
the last code below the delta flag; later kinds take 32+; migration 0033).
No section may use the letter `b` (every blob strips it: a delta's base).
`pre17ContentHash` keeps re-uploads of older captures no-ops. Capture
1.8.0-1.11.0: gi_collections' `crafting`, `musicGame`, `furnishingSets`,
`companionRewards`, `npcsMet` and the TCG's `levels`/`bosses`/`tavern` are
collections2 parts `k`/`y`/`e`/`o`/`n`/`v` (the deployed TCG part `g`
refuses new flags, hence `v`), gi_tasks' `signIns` is tasks letter `i`,
gi_exploration's `domainsCleared`/`tribalChapters` are exploration parts
`d`/`t`, and the new top-level `gi_teapot` / `gi_miliastra` are the
`extras` section (kind 32, the first code past the delta flag's range;
migration 0034; later top-level keys append a part there).
`pre18ContentHash` keeps re-uploads no-ops. Deck and team names are the
player's text, stored as is; a part
that fails its checks is dropped, never the upload. A file
without them stores and hashes exactly as before
they existed, and exports (GOOD rebuild, zip) write them back after
`timestamp`. The app uses them for the achievements' real completion times,
friendship and obtained dates on Characters, the planner's AR/WL (when the
settings are empty) and resin, the Anecdotes checklist (captured progress
plus hand marks in `anecdote_marks`), and the planner's Tasks: the newest
capture's `gi_tasks` ticks Daily Commissions (all done today) and the Spiral
Abyss (full stars in the running period) and adds Expeditions, Realm Currency
and Welkin Moon rows (Capture 1.7.0: Trounce Domains counts the weekly
boss discounts used, and an Adventure Rank rewards row lists unclaimed
ranks), while the capture is newer than the row's hand state
(`components/planner/tasks.ts` `captureRead`), and Collections
(`/app/a/:id/collections` = a card per collection with its figure,
`/collections/<tab>` = its page; Achievements is a card too): World
(`gi_exploration` against `@gdt/game-data` v7.1.17's cities, areas,
offerings and scene points: each visited scene's Teleport Waypoints,
domains and areas revealed, Statues of The Seven, reputation, offerings,
exploration per area as points over `exploreTotal` (capped at 100%), Statues
against `statueMaxLevel`; `src/data/world.ts`; plus bosses' and elites'
respawns from `gi_tasks.respawns`, named by the farming data), Events
(`gi_events`: window and reward counters, named by game-data `events` (else
the notice board when one notice matches the dates); `src/data/events.ts`), Hangout Events
(chapters, endings by `hangoutCgs` name, pictures), Furnishing Blueprints
(learned of the game data's 1,405), monsters seen on Living Beings, Radiant
Spincrystals (which the newest capture has, which are missing), Anecdotes
(the old `/anecdotes` page redirects there), the Archive, the Adventurer
Handbook, Living Beings (defeats), TCG, the wardrobe and Aranara, each from
the newest snapshot with that part, against `@gdt/game-data/collections`
(names in every language, icons, totals; `src/data/collection-names.ts`):
each Archive tab, TCG cards and wardrobe kind shows All / Missing / Have, and
a Recipes tab (Capture 1.5.0) shows unlocked, locked and mastered recipes.
Aranara entries stay numbered (the game names none); all the game data
lists show, those the capture lacks as not found. Radiant Spincrystals,
Anecdotes and Aranara link to guides (the Fandom wiki; the Aranara to Game8's Mysterious Clipboard page)
(`src/lib/wiki.ts`: page titles are the game's English names).

Character, weapon and material keys are stored as ids from the static,
append-only dictionary in `packages/shared/src/dictionary`; artifact sets,
slots and stats likewise for the catalog. Add new keys with
`pnpm --filter @gdt/shared dictionary --material new-keys.json` (or
`--artifactSet`; never edit the lists by hand; a test pins them). Keys the
dictionary lacks are stored as strings, so imports never fail on new game
content.

Reads are built for the browser to do the work: `/api/accounts/:id/catalog`
(every artifact, compact rows), `/api/accounts/:id/bundle?format=2` (stored
sections, untouched, in the binary GDT2 format of
`packages/shared/src/codec/bundle.ts`; without `format` an app from before v2
gets GDT1, the v2 sections decoded into the v1 form for it) and
`/api/accounts/:id/snapshots` (summaries). Each revalidates with an ETag on
the account's `data_version`, so a reload costs one indexed read. Bulk export
zips are built in the browser; the server only rebuilds single GOOD files.

## API notes

- **Auth.** Username + password, email optional (unique when set, also a login
  name). The password is sent over HTTPS and hashed by the Worker with Argon2id
  (19 MiB, 2 passes; `PASSWORD_PEPPER` is Argon2's secret input), stored as a
  PHC string; a login under older parameters rehashes. About 200 ms CPU per
  sign-in on Workers. Unknown logins still spend a full hash.
- **Sessions** (`worker/lib/session.ts`). Two HS256 JWTs in HttpOnly cookies,
  told apart by a `typ` claim: access `gdt_at` (15 min, path `/api`, verified
  without D1) and refresh `gdt_rt` (30 days, path `/api/auth`, SameSite
  Strict). Both carry `sid`, the device's row in `user_sessions` (migration
  0019: method password / discord / google / reset / legacy / irminsul, user agent, IP
  and first IP, `request.cf` country and city, created, last seen, expiry,
  revoked), and `users.token_version`. A refresh is one `UPDATE … RETURNING`
  of that row (active, unexpired, version current); it slides the expiry and
  records where the device is now (`session_revoked` otherwise). Every
  sign-in makes a row (ending the session this browser held before, and past
  30 active sessions the least recently seen). `GET /api/auth/sessions` lists
  them (with `current`), `DELETE /api/auth/sessions/:id` signs one device out
  (its own: a logout), `POST /api/auth/sessions/revoke-others` signs out every
  other device (bumps the version, so devices without a row go too) and
  keeps this one. Logout ends this device's row (a copied refresh token is
  refused); a password change and a reset keep this device and end the rest;
  `logout-all` ends all. Routes behind `requireActiveSession` (password,
  profile, sessions, identities, OAuth link, import-key creation; the staff
  routes) check the row in D1; everything else stays JWT-only, so a
  signed-out device can still read data until its access token runs out
  (≤15 minutes) — but its live socket closes at once. A token without `sid`
  (signed in before rows existed) gets one deduped `legacy` row at its next
  refresh, unless issued after `LEGACY_CUTOFF_S`; that path is deleted after
  2026-11-20. `users` also keeps `signup_ip`, `signup_country` and
  `last_active_at` (written at most hourly). Cookie-authed writes need
  `x-gdt-csrf: 1`.
- **Irminsul contract** (`irminsul/src/monitor.rs`): `POST
  /api/genshin-accounts-public/import-by-key` (multipart `file` + optional
  `timestamp`, header `x-import-key`) and `GET .../verify-key`. Any 2xx is
  success; 401/403 makes irminsul re-verify. Re-uploading a capture is a no-op
  (also when it was first stored before the extra keys were kept). Responses
  only gain fields: an import whose `gi_player.uid` is not the account's UID is
  stored anyway and answers with `warnings: [{code: "uid_mismatch", …}]` (also
  logged); an account's UID is never set from a file. Import keys are stored as
  SHA-256 and shown once.
- **Import keys, two kinds.** An account key (`gdt_ik_…`, `POST
  /api/accounts/:id/import-key`) always uploads to its account. A user key
  (`gdt_uk_…`, one per user: `POST /api/me/import-key` makes or replaces it,
  `DELETE` revokes; `hasImportKey` on `/auth/me`) uploads to the user's account
  whose UID is the file's `gi_player.uid` (irminsul ≥ develop d7c2bda), and a
  new UID makes a new account (no name, server read off the UID). A file
  without that UID is a 422 `uid_required`. A key is looked up among accounts,
  then users, in one round trip. Imports by key answer with the `account`
  they went to (`{id, name, uid, created}`); `verify-key` adds `scope`
  (`"account"` | `"user"`), and a user key answers `accountId`, `uid` and
  `server` as null with `dashboardUrl` the account list. A user's accounts
  have distinct UIDs (unique index, migration 0007): a duplicate is a 409
  `uid_taken`.
- **Imports** take two D1 round trips in the usual case; an identical later
  capture only moves `last_seen_at`. Uploads may be gzipped.
- **Upload limits.** Per file: 10 MB, and `GOOD_LIMITS` (`packages/shared/src/import.ts`,
  about 1.5× what the game holds: 200 characters, 3,000 weapons, 4,050
  artifacts, 11,100 material keys, 3,020 achievements, 6 substats; a key no
  dictionary knows and `source` at most 64 characters): over is a 422
  `too_many_items` / `key_too_long`. Per user (`worker/services/upload-limits.ts`,
  migration 0018): 1,000 new snapshots and 20 MB newly stored a UTC day (429
  `daily_upload_limit`, `Retry-After` to 00:00 UTC; counted in
  `user_upload_days` by the import's own batch) and 200 MB stored in all
  (sections + catalog chunks; 413 `storage_quota`). Only an upload that would
  store something is checked or counted; the one that crosses a limit is
  stored. The usage is read in the import's first batch: no extra round trip.
  A `site_settings` row overrides a default (`upload.daily_snapshots`,
  `upload.daily_bytes`, `upload.storage_quota`: a non-negative integer as
  text), `users.storage_quota` one user's storage quota. Bursts: 20 uploads a
  minute per import key (`KEY_IMPORT_LIMITER`), 60 a minute per account from
  the website and 60 key checks (`verify-key`) per key (`IMPORT_LIMITER`).
- **Live updates.** `GET /api/live` is a WebSocket (session cookie, this
  site's `Origin`) to the user's `LiveHub` Durable Object: one per user,
  SQLite-backed (as the Free plan requires), on the Hibernation API, with a
  `ping` → `pong` auto-response, so idle sockets cost nothing. A browser holds
  one socket for all its tabs (the tab holding the Web Lock `gdt-live:<user>`
  connects and relays over BroadcastChannel; the next tab takes over when it
  closes). Every write that moves an account's `data_version` or the account
  list (imports by key or from the dashboard, captures seen again, deletes,
  account create, rename, delete) tells the hub after the response
  (`waitUntil`; a failure is only logged), which sends `{type: "data",
  accountId, dataVersion, takenAt?}` or `{type: "accounts"}` to the user's
  sockets; tabs then re-read `GET /api/accounts` (one D1 round trip, an ETag
  over its body: a 304 when nothing changed). Costs are kept down by:
  `users.live_since` (migration 0010), set by the hub on its first socket and
  cleared after its last, read by imports and deletes in the batch they
  already send, so nothing calls the hub while no page is open; a `hello`
  (each account's version and names, read in the hub's one connect round
  trip) that tells a reconnecting browser whether it missed anything, instead
  of a catch-up read; dashboard import runs uploading with `x-gdt-live: quiet`
  and announcing once at the end (`POST /api/accounts/:id/announce`); a ping
  every 5 minutes only while some tab is visible. Sockets outlive the 15-minute
  access token: each keeps its session's token version and `sid` (the access
  token's `ver` and `sid`). Ending sessions (sign out everywhere, a password
  change) tells the hub, awaited, to close older ones (4003; the device that
  kept its session stays connected); ending one session (`revokeSession`)
  closes that session's sockets. Connects with an older version or a revoked
  row are refused (the connect's one round trip joins the row; a set of
  sessions revoked in the last minute covers a connect already past that
  read), and import events carry the current version too. On a 4003 the page
  refreshes and signs out if that is refused.
- **Diagnostics.** `GET /api/health` is public (status, build, D1, migrations).
  With `x-diag-key: <DIAG_KEY>` it adds the private tier — every secret with its
  value, bindings, error detail — and imports add `Server-Timing` and
  `x-gdt-d1` (round trips, rows read/written, SQL time). A session never opens
  it. The key lives in the gitignored `apps/tracker/.diag-key`:
  `curl -H "x-diag-key: $(cat apps/tracker/.diag-key)" https://teyvat.me/api/health`.
- **Progress** (cookie auth, account owner only):
  `GET/PATCH /api/accounts/:id/achievement-marks` (`{done, undone}` id lists;
  marks by hand, on top of what snapshots captured) and
  `GET/PATCH /api/accounts/:id/planner-targets` (`{upsert, remove}`; character
  and weapon goals, weapons keyed by owner), and
  `GET/PATCH /api/accounts/:id/planner-state`: the Planner's hand edits on top
  of the newest capture (`{base, inventory, current, prune}`: material counts
  set or added to, and goals' current state). `base` is the newest capture's
  `lastSeenAt` the edit was made against; when a newer capture has landed the
  whole request writes nothing (409 `capture_changed`), and a newer capture
  replaces older count edits (irminsul is the truth; table
  `inventory_adjustments`, column `planner_targets.current`, migration 0011).
  None of these bumps the account's `dataVersion`; planner writes send a
  `planner` live event naming the tab that made them (`x-gdt-tab`). Account
  settings also hold `traveler` (`F`/`M`), which picks the Traveler's portrait.
- **Maintenance** runs daily (cron): snapshots deleted more than 30 days ago
  are purged, unreferenced sections (v1 and v2, bases kept while anything
  needs them) are collected, upload-quota days older than 90 days are
  dropped, session rows (IPs included) go 7 days after they ended, sign-up
  IPs 90 days after the sign-up, and with `REPACK_CRON_LIMIT` set, v1 rows
  are repacked (see Storage model).
  Account counters are kept exact by triggers (migration 0002).

## Wish history

The wish history is a log beside the snapshots (it never moves an account's
`dataVersion`). It arrives from irminsul, which reads the game's wish history
API with the key the game hands out when Wish → History is opened (the key
never reaches the tracker), or from a file.

**Storage** (`@gdt/shared` `src/wish/`, `worker/services/wishes.ts`, migration
0023). `wish_histories` holds an account's clock (hours from UTC, set by its
first import) and a version (the ETag, and the guard concurrent imports
check). `wish_chunks` holds the pulls per account and UIGF banner type (100,
200, 301 with 400, 302, 500) in pull order, at most 512 to a row (`seq` 0, 1,
…; all but the last full). A chunk is a format byte (1 stored, 2 raw DEFLATE)
and: a palette of the chunk's items, most pulled first (a dictionary id from
the static CHARACTERS / WEAPONS lists, or an item the table doesn't know kept
as its name, rank, type and item id), then per pull one head varint (palette
index, the 400 bit, a synthetic-id bit), the seconds since the previous pull,
and the id (the game's ids lead with the pull's time, so it is stored as hi
and lo parts relative to the time: about 0 and 1 within a ten-pull).
Rank, type, name, item id, UIGF type and pity are derived on read
(`src/wish/items.json`: GOOD key, English name, rarity, item id). Measured on
a synthetic 5,000-pull history: 2.6 bytes a pull. Wish bytes count toward the
storage and daily byte quotas (not the snapshot count). An import reads each
banner's last chunk and rewrites only from the first chunk that changed;
older chunks are read only for records older than the last chunk.

**Ids.** The game's ids are 19-digit decimals above 10^18. Sources without
ids (paimon.moe's CSV and backup) get synthetic ones the game never uses:
`10^17 + seconds × 10^7 + banner index × 10^6 + n` (banner index 0-4 for 100,
200, 301, 302, 500; `n` the pull's place among that second's synthetic
pulls). They are matched by what they are (banner, time, item, and which of
that item within the second), so the same file twice adds nothing, and a real
record that matches one replaces it. Any id below 10^18 that arrives is
treated the same way. The sync cursor counts only real ids, so irminsul then
fetches what the API still has and replaces the made-up ids.

**API.** irminsul, signed in (`Authorization: Bearer`, routed by the
session's upload target as `/api/irminsul/import` is) or with an import key
(`x-import-key`, account- or user-scoped like uploads); one resolver for
both, `worker/lib/uploader.ts`:
`GET /api/wishes/cursor?uid=` → `{uid, accountId, newest: {"100"…"500": id |

## Live sync

While irminsul runs, it sends the account's changes between snapshots
(`POST /api/irminsul/changes`, Bearer or `x-import-key`), and the pages show
the newest snapshot with them applied. Plan and contract:
`docs/plans/live-sync.md` (§13 is the wire contract as built).

- **Per account**, setting `liveSync` (default `LIVE_SYNC_DEFAULT` in
  `packages/shared/src/settings.ts`); off, imports answer without `live` and
  batches with `{ok: false, live: false}`, and irminsul keeps to snapshots.
- **Storage**: the separate D1 database `gdt-live` (binding `LIVE_DB`,
  `worker/db/live-schema.ts`, migrations in `migrations-live/`, applied by
  `deploy.yml` after the main ones). One journal row per account (the base
  snapshot, seq, running chart figures, the base's guid → fingerprint index),
  batch rows merged per 10 minutes (deleted at the next snapshot), and chart
  points packed one row per account per UTC day. No foreign keys into `gdt`:
  deleting a base snapshot, an account or a user deletes their rows here
  (`services/live-sync.ts`).
- **Limits**: `LIVE_LIMITER` 20 batches/60 s per key or session, 2,000 per
  account per UTC day (429 `daily_live_limit`), a batch ≤ 2,000 changes and
  512 KB; the journal asks irminsul for a snapshot (`collapse`) when older than
  3 h with over 500 paths, or past 1 MB. `gdt-live` bytes count toward the
  storage quota (read beside the import's lookup).
- **Reading**: `GET /api/accounts/:id/live` (merged changes, ETag
  base + seq), `GET /api/accounts/:id/points?from=&to=`; `DELETE` either.
  Live socket event `{type: "live", accountId, seq}`.

## Account recovery

**Paused.** Email costs money, so the email features are off unless the Worker
var `EMAIL_FEATURES` is `"1"` (unset in `wrangler.jsonc`, tests and `vite dev`;
`EMAIL_FEATURES=1` in `.dev.vars` turns them on locally). While off: sign-up
has no email field and the API ignores an `email`; Settings can't add or change
one (`PATCH /api/auth/profile` answers 403 `email_paused`), only remove one set
before, which still signs in; `forgot-password`, `verify-email/send` and
`verify-email` answer 404 `email_paused` and their pages go to `/login`; no mail
is sent even with the binding. The sign-in page and Settings → Connected
accounts point at Discord / Google instead. **Admin reset** links keep working
(`reset-password`, `reset-password/check`, `/reset-password?token=…`). To turn
email on: the steps below, plus `"vars": { "EMAIL_FEATURES": "1" }`.

One-time links (table `auth_tokens`, migration 0014; only the token's SHA-256
is stored): email confirmation (24 h; sent at sign-up, on an email change and
by Settings' Verify, at most 3 an hour) and password reset (30 min, mailed only
to a **confirmed** email, at most 3 an hour per account). "Forgot password"
answers the same at once whatever was typed; the lookup and mail run after the
response. A reset sets the password, bumps `token_version` (every session and
live socket ends), uses up the user's other reset links, mails a notice and
signs that browser in. Changing the password in Settings also ends open reset
links. Routes: `worker/routes/recovery.ts`.

**Email** goes out through Cloudflare Email Service (Workers Paid). Until the
binding exists nothing is sent and Settings says email isn't available; to
turn it on:

1. Dashboard → Compute → Email Service → Email Sending → Onboard Domain →
   `475.dev`. Cloudflare adds the records itself (MX + SPF on
   `cf-bounce.475.dev`, DKIM `cf-bounce._domainkey`, DMARC `_dmarc`); wait for
   them to verify.
2. Add to `apps/tracker/wrangler.jsonc`:
   `"send_email": [{ "name": "EMAIL", "allowed_sender_addresses": ["no-reply@475.dev"] }]`
   (optional vars: `EMAIL_FROM`, `SITE_URL`), run `pnpm --filter @gdt/tracker
   cf-typegen`, push.

`vite dev` simulates the binding: each mail is logged in the dev server's
output with the path of its text and HTML files, nothing is sent.

**Admin reset** (also for users without an email): prints a link valid for 24
hours that sets a new password once; send it privately (e.g. on Discord). The
admin never sees or sets the password. Staff with `users.reset_password`
make the same link from the dashboard (a user's page, Reset link).

```bash
pnpm --filter @gdt/tracker admin:reset-link <username|email>           # production D1
pnpm --filter @gdt/tracker admin:reset-link <username|email> --local   # dev database, localhost link
```

## Sign in with Discord / Google

Optional: a provider is on only while the Worker has both its secrets, and the
app shows its button only then (`GET /api/auth/oauth/providers`). With none
set, nothing changes. Code: `worker/lib/oauth.ts` (flow, cookies),
`worker/routes/oauth.ts`, `worker/services/identities.ts`, table
`user_identities` (migration 0015).

- **Flow.** Authorization code with PKCE (S256) and `state`; Google's is
  OpenID Connect (`openid email profile`, a `nonce`, the ID token from the
  token endpoint checked for issuer, audience, expiry and nonce); Discord's
  user comes from `users/@me` (`identify email`). State, verifier, nonce and
  intent sit in `gdt_oauth` (HS256 under a key derived from `JWT_SECRET`,
  HttpOnly, Secure, SameSite Lax, path `/api/auth/oauth`, 10 minutes). The
  redirect URI is fixed: `<site>/api/auth/oauth/<provider>/callback`, from
  `SITE_URL` or the production origin (loopback under `vite dev`).
- **Linked** provider account: signs its user in like a password login.
- **Not linked**: never matched by email. `/oauth` offers a new account (no
  password; the username is suggested from the provider, the provider's email
  can be set as the account's, unconfirmed, with a confirmation link mailed,
  while the email features are on)
  or "I have an account" (password sign-in that links it). The provider
  account waits in `gdt_oauth_pending` (15 minutes), never in a URL.
- **Settings → Connected accounts**: Link (needs the session; the callback
  must find the same user in the same session, else `oauth_error=session`) and
  Unlink, refused while it is the only way in (no password, no other
  provider). An account without a password gets "Set password" (session only).
  Linking or a first password mails a notice to a confirmed email. Nothing
  here ends a session.

**Setup** (the redirect URIs must match exactly):

1. Discord: <https://discord.com/developers/applications> → New Application →
   OAuth2 → Redirects: add
   `https://teyvat.me/api/auth/oauth/discord/callback` and the old
   `https://genshin-tracker.475.dev/api/auth/oauth/discord/callback` (and
   `http://localhost:5173/api/auth/oauth/discord/callback` to try the real
   one locally). Copy the Client ID; Reset Secret for the Client Secret.
2. Google: <https://console.cloud.google.com> → new project → Google Auth
   Platform (OAuth consent screen): External; app name, support email,
   authorized domains `teyvat.me` and `475.dev`, developer contact; Data access: `openid`,
   `.../auth/userinfo.email`, `.../auth/userinfo.profile`; Clients → Create
   client → Web application → Authorized redirect URIs:
   `https://teyvat.me/api/auth/oauth/google/callback`, the old
   `https://genshin-tracker.475.dev/api/auth/oauth/google/callback` (and the
   localhost one). Audience → Publish app (these scopes need no review).
3. From `apps/tracker`: `pnpm exec wrangler secret put DISCORD_CLIENT_ID`
   (then `DISCORD_CLIENT_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`).
   A secret takes effect at once, no redeploy. Apply migration 0015 first
   (CI does on the next push).

`vite dev` uses a fake Discord and Google (`dev/oauth-mock.ts`, pick who signs
in); `OAUTH_DEV_MOCK=0` in `.dev.vars`, with the four secrets there, uses the
real ones.

## Sign in from irminsul

irminsul (the desktop capture app) signs in with the tracker instead of a
copied import key: OAuth 2.0 authorization code with PKCE (RFC 7636) for a
public client answering on a loopback port (RFC 8252). The wire contract is
shared with irminsul; responses only gain fields. Code:
`worker/routes/irminsul-oauth.ts`, `worker/routes/irminsul.ts`,
`worker/lib/irminsul-auth.ts`, `worker/services/irminsul.ts`; the page is
`src/views/LinkView.vue`, the query check `parseLinkQuery` in
`packages/shared/src/irminsul.ts`. Migration 0022.

1. irminsul reads `GET /api/oauth/irminsul` (discovery: `authorize_url`
   `<origin>/link`, `token_url`, `revoke_url`, `client_id: "irminsul"`,
   `version: 1`, absolute URLs from the request's origin), listens on
   `127.0.0.1:<free port>` and opens
   `/link?client_id=irminsul&redirect_uri=http://127.0.0.1:<port>/callback&state=…&code_challenge=<S256>&code_challenge_method=S256&device=<PC name>`.
2. `/link` checks the query first (client, a loopback `…/callback` redirect —
   `127.0.0.1` or `localhost`, any port, nothing else — an S256 challenge, a
   state); a bad link is an error card and is never followed. Signed out, the
   router sends it to sign-in (`?next=/link…`; password, Discord / Google, the
   human check, sign-up all come back). Then one consent card: "Irminsul on
   <PC>", uploads go to **Auto: match the account by UID** (preselected) or
   **Always this account**, Allow / Cancel. The page refuses to show inside a
   frame, and `/link` is sent with `X-Frame-Options: DENY`.
3. Allow is `POST /api/oauth/authorize` (session cookie, CSRF header, an active
   session; 400 `invalid_request` / `invalid_redirect` / `invalid_account`, 403
   `account_suspended`): a one-time code (`oauth_codes`, SHA-256 only, 60 s,
   bound to the user, challenge, redirect, PC name and target), answered as
   `{redirect: "<callback>?code=…&state=…"}`, where the page goes. Cancel goes
   to `<callback>?error=access_denied&state=…`.
4. irminsul exchanges it at `POST /api/oauth/token` (JSON or form-encoded)
   `{grant_type: "authorization_code", client_id, code, code_verifier,
   redirect_uri}`. The code is used up by the first try, right or wrong; a
   second use ends the session the first made. It makes a `user_sessions` row
   with `method = 'irminsul'`, `user_agent` "Irminsul on <PC>", `device_name`,
   `upload_mode` (`uid` | `account`) and `upload_account_id`, and answers
   `{token_type: "Bearer", access_token, expires_in: 900, refresh_token,
   refresh_expires_in: 2592000, whoami}`. `grant_type: "refresh_token"` swaps
   the refresh token for a new one (only its SHA-256 is kept,
   `refresh_hash`) and slides the row's 30 days, in one `UPDATE … RETURNING`;
   the token before the current one coming back (`refresh_prev_hash`) means a
   copy is in other hands and ends the session. Errors are OAuth's `{error,
   error_description}`: 400 `invalid_grant` (wrong, expired, used or rotated
   away, signed out), `invalid_request`, `unsupported_grant_type`; 403
   `account_suspended`.
5. `GET /api/irminsul/whoami` and `POST /api/irminsul/import` take
   `Authorization: Bearer <access>`. whoami answers the verify-key fields
   (`accountId, accountName, uid, server, dashboardUrl`) plus `scope` (`uid` |
   `account`), `user` and `configUrl`: `/app/settings/devices?device=<sid>`
   (the old `/app/settings?device=<sid>#devices` redirects there), that
   session's row in Settings → Devices, the only place its target is
   changed (`PATCH /api/auth/sessions/:id {upload: {mode: "uid"} | {mode:
   "account", account_id}}`, irminsul rows only). The import is
   `import-by-key`'s, shared code and all (`services/upload-as.ts`): uid mode
   is a user key (by `gi_player.uid`, new UIDs make an account, 422
   `uid_required` without one), account mode an account key (409
   `upload_target_missing` once that account is deleted); the same file
   limits, daily and storage quotas, warnings and live notify; 20 uploads a
   minute per session (`KEY_IMPORT_LIMITER`). Both read the session row in the
   one round trip a key's lookup costs: 401 `token_expired` (refresh, retry
   once), 401 `session_revoked` (signed out), 403 `account_suspended` /
   `uploads_blocked`.
6. `POST /api/oauth/revoke {token}` (irminsul's Sign out) ends the session;
   200 whatever the token (RFC 7009).

The two worlds stay apart: irminsul's access token is a JWT with `typ` and
`aud` `irminsul` that only the `/api/irminsul` routes read, from the header;
those routes never read a cookie, and the cookie routes never read the header.
Its refresh token is opaque (`gdt_irt_<sid>_<random>`). An irminsul session is
a device like any other: Settings → Devices lists it ("Irminsul on <PC>",
last seen, place, its target) with Sign out; "Sign out other devices", a
password change, `logout-all`, a suspension and the 30-session cap end it;
maintenance deletes its row 7 days after it ended, and codes a day after they
expired.

Import keys stay: released irminsul builds keep calling
`/genshin-accounts-public/import-by-key` and `verify-key` (unchanged), other
tools can build on keys, and irminsul keeps a saved key working until the user
signs in.

## Account sharing

An owner shares an account by username (Manage → Account sharing; plan in
`docs/plans/account-sharing.md`). Migration 0029 adds `account_members`
(`account_id`, `user_id`, `role` viewer|editor, `invited_by`, `created_at`,
`accepted_at`; NULL = a pending invite, gone after 14 days, deleted by
maintenance). `genshin_accounts.user_id` stays the owner.

- **Access** is checked per request in one query: `loadAccount` /
  `assertAccount(db, user, account, need)` in `worker/services/accounts.ts`,
  `need` = `view` (any access) | `edit` (owner, editor) | `own`. No access is
  a 404, too little a 403 `account_read_only` / `owner_only`. Editors upload,
  plan, mark achievements/anecdotes, set the Traveler and import wishes;
  renaming, keys, the live-sync switch, deleting snapshots/chart points/wishes,
  sharing and deleting the account are the owner's. `worker/test/sharing.test.ts`
  walks every account route as stranger, viewer, editor: add a new route there.
- **Routes** (`worker/routes/sharing.ts`): `GET/POST /api/accounts/:id/members`,
  `PATCH/DELETE /api/accounts/:id/members/:userId` (a member deleting
  themselves = leave), `GET /api/invitations`,
  `POST /api/invitations/:accountId/accept|decline`. Limits: 8 members per
  account, 20 pending invites per owner. Members see accepted members only.
- **Lists**: `GET /api/accounts` and the bootstrap list owned and shared
  accounts (`accessibleAccountsSql`, a UNION over both indexes) with `access`
  and, on shared ones, `owner`; the bootstrap also answers `invitations`.
- **Live**: `listenerStatement` reads the owner and every accepted member;
  `notifyAccount` sends to each one listening, `notifyAccountLater` when the
  write read none. Sharing changes send `accounts` to both sides.
- **Uploads**: a user key / irminsul "Auto by UID" picks the uploader's own
  account with the UID, else the one shared with them as editor
  (`pickByUid`); a view-only match is 403 `account_read_only` (no silent
  duplicate). "Always this account" may name a shared editor account
  (`editableBy`). Storage, daily limits and gdt-live bytes count for the
  account's owner.
- **App**: shared accounts are grouped under "Shared with me" in the switcher
  (a dot when invites wait; Home lists them with Accept/Decline); a viewer's
  pages are read-only (`useReadOnly`, as staff Inspect), owner-only controls
  check `useAccess()`.

## Human check (Turnstile)

Cloudflare Turnstile on sign-up (`/register`, action `register`), password
sign-in (`/login` and `/oauth/pending/login`, action `login`) and a new
account through Discord / Google (`/oauth/pending/register`, `register`).

Worker has **both** secrets `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`;

(`turnstileSiteKey`). Code: `worker/lib/turnstile.ts`,
`src/components/auth/HumanCheck.vue`, `src/lib/turnstile.ts`.

- The widget is Managed with appearance interaction-only: invisible unless
  Cloudflare wants a click. The server checks each token with siteverify
  (visitor IP, 5 s timeout): success, the form's action and this site's
  hostname.
- No token: 400 `human_check_required` ("Reload the page to sign in / up",
  what an app cached from before shows). Refused: 403 `human_check_failed`.
  siteverify down: a sign-up gets 503 `human_check_unavailable`, a sign-in
  goes on (logged). A rejected secret logs `turnstile_secret_rejected`.
- Sign-in checks in this order: per-IP limit, human check, per-name limit,
  Argon2, so a bot without a token can't use up a name's budget.
- The submit button stays disabled (greyed, tooltip "Checking you're
  human…") until the widget holds a fresh token: while it loads, while a
  challenge shows, once a token expires and after each submit (a token works
  once). With the check off it is enabled as soon as the page knows. A
  blocked script or a failed run says so above the button
  (`human-check-state.ts` holds this logic, with tests).

**Setup:**

1. Ship the app with this code first and wait a few days, so cached PWAs

   page to sign in").
2. Dashboard → Turnstile → Add widget: name "Genshin Tracker", hostname
   `teyvat.me` and `genshin-tracker.475.dev`, mode **Managed**, no pre-clearance. Copy the
   site key and the secret key.
3. From `apps/tracker`: `pnpm exec wrangler secret put TURNSTILE_SITE_KEY`, then
   `TURNSTILE_SECRET_KEY` (paste at the hidden prompt). Both at once: with
   one only, the check stays off. A secret takes effect at once, no
   redeploy; deleting either turns the check off again.

`vite dev` uses Cloudflare's always-pass test keys (vite.config.ts); keys in
`.dev.vars` override them (site key `3x00000000000000000000FF` forces an

## Staff dashboard

`/app/staff` (lazy; a "Staff" link in the sidebar for whoever has
`staff.view`): Overview, Users (and one user's page), Storage, Roles, Audit,
and Inspect (someone's Characters, Weapons, Artifacts, Materials and
Snapshots, read-only). API: `/api/staff/*` (`worker/routes/staff.ts`), on
the session (`requireActiveSession`), never the diag key. Migration 0020.

- **Roles, Discord-style** (`worker/services/roles.ts`): a user's permissions
  are the union of their roles' nodes (`PERMISSION_NODES` in
  `packages/shared/src/staff.ts`; managing and deleting are always separate
  nodes); `position` is the hierarchy. Staff act only on users whose highest
  role is below theirs (never themselves), change and give only roles below
  theirs, and grant or take away only nodes they hold. Seeded: Owner (`*`,
  locked), Admin, Moderator, Support (editable).
- **Owner only from the command line** (the dashboard can't give it, so a
  stolen staff session never makes one; the last Owner can't be revoked):

  ```bash
  pnpm --filter @gdt/tracker admin:grant <username|email> <role> [--revoke]   # production D1
  pnpm --filter @gdt/tracker admin:grant <username|email> owner --local       # dev database
  ```

- **Enforcement.** Nodes are read from D1 on every staff request; without the
  node a route is a 404. Private fields (email, IPs, sessions, identities)
  need `users.view_private` and are never shown of a user as high as you.
  Every write, and every look at someone's data, writes an `admin_audit`
  row (no foreign keys: it outlives the users it names).
- **Actions.** Suspend (403 `account_suspended` on sign-in, Discord/Google
  sign-in, refresh, reset links and key uploads; ends every session and
  socket), block uploads (403 `uploads_blocked` for key and website
  uploads), reset an account's key or revoke the user key, a 24-hour reset
  link (shown once, the row `admin:reset-link` makes), rename, unlink a
  provider (not the last way in), delete users (one, or ≤100), storage
  quota, delete data now (snapshots by id or date, the trash, a whole
  account; sections collected in the same batch), the sign-up switch (Open /
  Discord-Google only / Closed) and the upload limits (`site_settings`).
  Users delete themselves in Settings (`DELETE /api/auth/account`).

script in `index.html`).

- **Interface text**: vue-i18n messages, one folder per language under
  `apps/tracker/src/i18n/locales/<code>/` (same files and keys as `en/`;
  English is built in, the others load on demand). `i18n/__tests__/messages.test.ts`
  checks every language has exactly the English keys and placeholders. Game
  terms in the messages follow the game's own translation in that language.
- **Game names** (characters, weapons, materials, achievements, anecdotes…)
  come from `@gdt/game-data`, compiled from the game's own text in each
  language; English shows where the game has none.
- **Fonts**: Outfit for Latin text; other scripts fall through to the
  system's font for that language (`main.css` `:lang(...)`); Vietnamese skips
  Outfit (no stacked diacritics).
- **Event titles** come from the game's notice board: English and Chinese per
  server, the other languages read once from one server (same notice ids).

A new message key needs a text in every language folder (the test fails
otherwise).

## PWA

`src/pwa/sw-template.js` is emitted as `/sw.js` by a Vite plugin with the
build's precache list: one cache per build, network-first navigation with the
app shell offline, `/api` never cached, and game images (from
static.nanoka.cc, and gi-cdn.475.dev for the few it lacks; both hosts are the
game data's `IMAGE_HOST` / `GI_CDN_HOST`, which the plugin writes into it)
cache-first in one bounded cache that keeps only image responses. A new build
waits until the user accepts the "new version" banner. `public/_headers` keeps
`sw.js` and the manifest uncached.

## Deploying

CI deploys: every push to `main` runs `.github/workflows/deploy.yml`, which
runs the CI checks, then `db:migrate:remote`, then `wrangler deploy` (the
manual order below). A game data bump merged by `game-data-bump.yml`
deploys the same way. Without the Cloudflare secrets the checks still run and
the deploy steps are skipped with a notice; deploy by hand instead.

Repository secrets (Settings → Secrets and variables → Actions):

| Secret | What |
|---|---|
| `GAME_DATA_DEPLOY_KEY` | Private half of a **read-only deploy key** on `tawan475/genshin-game-data` (install the private game data). Or `GAME_DATA_TOKEN`: a fine-grained token with Contents: read on that repository |
| `CLOUDFLARE_API_TOKEN` | Cloudflare API token from the "Edit Cloudflare Workers" template plus **Account · D1 · Edit**, for this account and the `teyvat.me` and `475.dev` zones (optional: without it CI doesn't deploy) |
| `CLOUDFLARE_ACCOUNT_ID` | The Cloudflare account id (`wrangler whoami`) |

Settings → Actions → General: "Allow GitHub Actions to create and approve
pull requests" (the bump workflow opens and merges one). `main` must accept
those merges (no required reviews).

By hand, from a checkout:

```bash
pnpm exec wrangler login
pnpm exec wrangler d1 create gdt --location apac        # once; put the id in wrangler.jsonc
pnpm exec wrangler d1 create gdt-live --location apac   # once (live sync); its id too
pnpm exec wrangler secret bulk secrets.json             # once: JWT_SECRET, PASSWORD_PEPPER, DIAG_KEY
pnpm --filter @gdt/tracker db:migrate:remote
pnpm --filter @gdt/tracker db:migrate:live:remote
pnpm --filter @gdt/tracker run deploy                    # type-check + build + wrangler deploy
```

The few icons static.nanoka.cc lacks load from gi-cdn.475.dev (the private
gi-cdn repo, which serves them to this site only). Deploy gi-cdn before a
tracker whose game data adds `hosted` names, or those show initials until it
is.

`wrangler deploy` also creates the `LiveHub` Durable Object class (migration
`v1` in `wrangler.jsonc`). Live updates need D1 migration 0010
(`users.live_since`): apply it (`db:migrate:remote`) before deploying.

Static assets and `/api` both run at the visitor's edge (no placement), for D1
read replication.

### D1 read replication

Turn it on for both databases (`gdt` and `gdt-live`): Cloudflare dashboard →
Storage & Databases → D1 → the database → Settings → Read replication →
Enable. The code works the same with it off.

Every `/api` request runs its queries on one D1 session per database
(`worker/lib/d1-session.ts`, mounted in `worker/index.ts`): writes (any
method but GET/HEAD) start at the primary, reads start at the newest
bookmark the browser holds, else at any replica. The browser holds bookmarks
in a cookie (`gdt_d1`, `gdt_d1l`; set by writes and sign-ins) and in
localStorage (`src/api/d1-bookmark.ts`), sent as `x-gdt-bookmark` /
`x-gdt-bookmark-live`; every answer returns its session's bookmarks in the same
headers, and every live event carries the bookmarks of the write it reports
(`d1`, `d1l`; `hello` too), so a page never reads older data than it wrote
or was told about. The Durable Object, cron and maintenance use the bindings
as they are (always the primary). Capture apps send no bookmark: their writes
start at the primary and their few reads may lag a replica by a moment.

### The old address

teyvat.me has been the site since 2026-10-25; genshin-tracker.475.dev stays
a custom domain of the same Worker for good, because irminsul builds already
installed post to its `/api` (import by key, verify-key, sign-in, wishes,
live sync). What each part does there:

- `/api/*` answers as on teyvat.me, on the same data. The links it gives
  irminsul for a browser (`dashboardUrl`, `configUrl`, discovery's
  `authorize_url`) point at teyvat.me (`pageOrigin` in `worker/lib/email.ts`);
  `token_url`/`revoke_url` stay on the host asked, as irminsul requires.
  Discord/Google sign-in started there still comes back there (`linkOrigin`:
  the flow cookie is per host), so its redirect URIs stay registered.
- Pages: a Redirect Rule answers 301 to teyvat.me, path and query kept.
  `index.html` does the same in script for a page a service worker or
  cache still holds.

The Redirect Rule (Cloudflare dashboard → the `475.dev` zone → Rules →
Redirect Rules → Create rule → Single Redirect), added only once sign-in on
teyvat.me works (Discord/Google redirect URIs, Turnstile hostname):

- Custom filter expression:
  `(http.host eq "genshin-tracker.475.dev" and not starts_with(http.request.uri.path, "/api/"))`
- Then: Dynamic, `concat("https://teyvat.me", http.request.uri.path)`,
  status 301, Preserve query string on.

Never let it cover `/api/`: shipped irminsul builds would lose uploads and
sign-in (clients don't follow a 301 on a POST). Outside this repo the move
also needed the `teyvat.me` zone on Cloudflare, the CI token allowed on it,
the Discord/Google redirect URIs, the Turnstile hostname and gi-cdn's
`ALLOWED_ORIGINS` (all done). Email, while paused, still sends from
`no-reply@475.dev` with links to teyvat.me; moving the sender to teyvat.me
means onboarding that domain to Email Sending and setting `EMAIL_FROM`.
